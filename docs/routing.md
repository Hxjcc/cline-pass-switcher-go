# 账号与渠道调度

网关收到一个模型请求后，要决定两件事：用账号池里的哪个账号发出，以及让 Cline 网关把请求交给哪个渠道（即背后实际提供模型的服务商）。本文说明这两件事如何决定，以及出错时怎样重试。

## 一次请求的过程

1. **确定候选渠道。** 根据该模型的渠道设置（`perModel`）得到一组候选渠道。没有设置时只有一个候选："交给网关自动路由"。同一会话上次成功的渠道会被挪到最前面（见[会话粘性](#会话粘性)）。
2. **按顺序尝试每个候选渠道。** 每次尝试先选一个账号（见[账号选择](#账号选择)），然后向上游发出请求。
3. **同一渠道换账号重试。** 上游返回 401、403 或 429 时，这个账号进入冷却，只要账号池里还有其他可用账号，就在同一渠道上换一个账号再试，每个渠道最多用 4 个账号。
4. **换下一个渠道。** 其他错误（5xx、网络错误、超时等）直接换下一个候选渠道。
5. **总次数上限。** 一次客户端请求最多向上游发出 `候选渠道数 × 每个渠道可换的账号数` 次调用，其中每个渠道可换的账号数等于可用账号数、最多 4 个，乘积最多 16 次。

下列情况会提前停止，把最后一次的错误返回给客户端：

- 没有任何可用账号：返回 503（`no_account`）。
- 渠道排除规则冲突：返回 400（见[渠道钉住与排除](#渠道钉住与排除)）。
- 401 / 403，且没有别的账号可换。
- 429，且该模型是[自动路由](#只能自动路由的模型)的模型：换渠道等于重复同一个请求。
- 请求使用的是[绑定了账号的代理密钥](#绑定账号的代理密钥)，且上游返回任何 4xx / 5xx。
- 客户端已经断开。

**流式请求一旦开始输出就不再切换。** 网关读到上游的第一个事件并转发给客户端之后，后续出错只会结束这个流，不会换账号或渠道重来。首个事件之前的失败仍按上面的规则重试。

## 账号选择

账号必须**已启用且填写了 API Key** 才会参与调度。

| 控制台中的模式 | `accountMode` | 行为 |
|---|---|---|
| 单账号 | `single` | 使用「当前账号」。它在冷却或配额已满时，按列表顺序使用第一个可用的账号。 |
| 账号池轮询 | `roundrobin` | 在所有可用账号之间轮流使用。在控制台保存账号设置后，轮询从头开始。 |

每次选择账号时依次考虑：

1. 请求带有绑定账号的代理密钥时，只用该账号，下面几步都跳过。
2. 同一会话上次使用的账号，只要它没在冷却、配额未满、仍然启用。
3. 按上表的模式选择，跳过冷却中和配额已满的账号。

**所有账号都在冷却或配额已满时，仍然会选一个账号发出请求**，而不是直接拒绝。上游是否接受由上游决定。

### 冷却

| 上游返回 | 冷却时长 |
|---|---|
| 401 / 403 | 10 分钟 |
| 429 | 2 分钟 |

冷却按账号计算，与渠道无关。账号下一次请求成功、或者在控制台更换了它的 API Key 时，冷却立即解除。冷却状态只保存在内存里，重启服务后全部清空。

### 配额

Cline Pass 套餐有 5 小时、7 天、30 天三个用量窗口。网关通过两个只读接口读取用量，不消耗模型额度：

- `GET /users/me/plan`
- `GET /users/me/plan/usage-limits`

**只有账号池里有两个及以上可用账号时，选号才会检查配额。** 任一窗口用量达到 100% 的账号会被跳过，直到该窗口的重置时间（上游返回的 `resetsAt`）；上游没有给出有效的重置时间时，先跳过 5 分钟。

读取频率有限制：选号时每个账号的读取结果复用 60 秒，单次读取超时 4 秒，一次选号最多检查 8 个账号、总共最多花 6 秒。读取失败时照常使用该账号，不会阻塞请求。

控制台「账号池」页打开时会读取一次配额（服务端结果缓存 30 秒），点击「查询配额」会跳过缓存立即重新读取。

## 会话粘性

请求体里带有 `prompt_cache_key` 时（Codex 每个会话都会带），网关把「模型 + 这个值」视为一个会话，记住它上次成功使用的**账号和渠道**，下一轮优先使用同样的组合，以便命中上游的提示缓存。

- 有效期 30 分钟，每次成功请求重新计时。
- 记住的账号在冷却、配额已满或被停用时，这一轮改用正常的选择；记住的渠道仍然排在最前面。
- 该账号收到 401 / 403、它的 API Key 被更换、或者服务重启后，记录失效。

## 模型订阅

`knownModels` 是订阅模型列表。`/v1/models` 返回的就是它，控制台「模型与上游」页展示的也是它。

- **订阅列表不是白名单。** 客户端请求列表以外的模型时，网关照样转发；如果是 `cline-pass/` 开头的模型并且请求成功，它会被自动加入订阅，即使之前被手动移除过。
- **拉取官方模型**会从三个公开来源收集 `cline-pass/` 模型：Cline 的推荐模型接口、models.dev 和 Cline 文档页。新发现的模型加入订阅，同时更新模型的显示名、上下文长度、推理档位等信息。手动移除过的模型不会被加回来。
- **移除模型**会同时删除它的渠道设置和已探测的信息。

## 渠道钉住与排除

每个模型可以在「模型与上游」页展开后单独设置，保存在 `config.json` 的 `perModel` 里。

| 设置 | 效果 |
|---|---|
| 优先渠道 | 按顺序逐个尝试。第一个失败时换下一个。 |
| 钉住模式：严格钉住（`strict`） | 每次尝试只允许当前这一个渠道。 |
| 钉住模式：优先 + 回退（`preferred`） | 当前渠道排在最前，其余优先渠道作为 Cline 网关自己的备选顺序。 |
| 排除渠道 | 这些渠道不会被使用。排除后没有剩余渠道时，请求直接返回 400（`no_allowed_channels`）；模型还没探测过、网关不知道有哪些渠道时，返回 400（`channel_list_unknown`）。 |
| 恢复自动 | 清空该模型的优先渠道与排除设置。 |

这些设置以 Cline 网关支持的路由参数发送给上游，是否生效取决于该模型在上游的路由方式。

### 只能自动路由的模型

有些模型的上游路由会忽略渠道偏好，或者只有一个渠道。探测后，控制台会在模型行上标出原因，并禁用钉住与排除：

| 原因 | 含义 |
|---|---|
| 网关已忽略上游偏好 | 网关不理会渠道参数，由网关自己选择。DeepSeek 系列目前属于这种情况。 |
| 仅有一个候选渠道，无需钉住 | 没有其他渠道可选。 |
| 没有可用渠道 | 探测没有发现任何渠道。 |
| 无法确认网关是否支持钉住 | 判断用的探测请求失败了，可以稍后重新探测。 |
| 无法识别路由线路 | 上游响应中没有可识别的路由信息。 |

对于网关已忽略偏好的模型，网关不再附带渠道参数，每次只发一次请求；已保存的渠道设置保留在配置里，但不生效。没有探测过的模型按已保存的设置发送。

### 探测和校验会产生费用

下列操作都会向上游发出真实的模型请求，按正常请求计费：

| 操作 | 位置 | 请求内容 |
|---|---|---|
| 探测渠道 | 模型行的操作按钮、「批量探测」（一次同时探测 3 个模型） | 一次最多 256 token 的请求，读取路由信息；再用一个不存在的渠道发一次最多 16 token 的请求，判断网关是否支持钉住。 |
| 校验全部渠道 | 模型行的操作按钮 | 对每个候选渠道各发一次最多 16 token 的请求。 |
| 发送测试请求 / 测试台 | 模型行、「测试台」页 | 一次普通请求，按该模型当前的渠道设置路由，记入请求历史（类型为 `test`）。 |
| 测试账号 | 「账号池」页 | 用该账号向第一个订阅模型发一次最多 512 token 的请求。 |

读取配额不消耗模型额度。

## 绑定账号的代理密钥

在「代理密钥」页可以把一个客户端密钥绑定到某个账号。使用这个密钥的请求：

- 只用绑定的账号，不参与会话粘性、配额跳过和轮询。
- 上游返回任何错误都直接返回给客户端，不换其他账号，避免花掉别人的额度。
- 绑定的账号被停用或删除时，请求直接被拒绝。

## 超时

| 阶段 | 时长 | 说明 |
|---|---|---|
| 连接与 TLS 握手 | 各 15 秒 | |
| 流式请求：等待第一个事件 | 180 秒 | 超时算作这次尝试失败，可以换渠道重试。 |
| 流式请求：两次事件之间的静默 | 300 秒 | 推理模型可能长时间不输出，所以只按"没有数据"判断卡住，不限制流的总时长。 |
| 非流式请求：总时长 | 600 秒 | |

流式响应期间，网关每 10 秒向客户端发送一次 SSE 注释行（`: ping`），防止中间的代理因为长时间没有数据而断开连接。

## 响应头

网关在响应中附带以下头，方便排查实际路由：

| 响应头 | 含义 |
|---|---|
| `X-Cline-Account` | 最终使用的账号名称。 |
| `X-Cline-Target-Upstream` | 计划尝试的渠道，多个用 `>` 连接；自动路由时为 `auto`。 |
| `X-Cline-Actual-Upstream` | 上游实际使用的渠道，未知时为 `unknown`。 |
| `X-Cline-Canonical-Model` | 上游报告的规范模型名。 |
| `X-Cline-Attempts` | 这次请求实际向上游发出的调用次数。 |
| `X-Cline-Reasoning-Effort` | Responses 接口实际发给上游的推理档位。 |

流式请求的响应头在第一个事件到达时就发出，此时还不知道实际渠道和规范模型，所以通常只有前两项和 `X-Cline-Attempts`；这些信息会记在请求历史里。
